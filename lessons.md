- [2026-08-07]: Beim Aufraeumen auf ein einziges Ausgabeformat habe ich `chatTargetSchema` von drei auf einen Wert verengt, die Beispiel- und Testconfigs angepasst — und die **laufende** `/data/providers.yaml` vergessen. Die trug noch `chatTarget: googleChat`. Der Container ging beim Deploy in einen Restart-Loop (`Configuration is invalid`), rund sechs Minuten lang, bis ich es bemerkte. Der `CHAT_TARGET`-Env-Override haette gerettet, greift aber erst **nach** der Schema-Validierung. Bitter daran: genau dieses Verhalten hatte ich zwei Stunden vorher als Test festgeschrieben („eine Installation, die noch teams konfiguriert hat, soll laut scheitern") — ich hatte nur nicht gesehen, dass unsere eigene Installation dieser Fall ist. → **Wenn eine Schemaverschaerfung landet, gehoert die laufende Konfiguration vor den Deploy**, nicht danach: `docker exec <container> cat /data/providers.yaml` gegen das neue Schema pruefen (oder `node dist/src/main.js validate` mit der echten Datei), bevor das Image getauscht wird. Und: Beispieldateien im Repo sind nicht die Produktion — bei zustandsbehafteten Volumes ist die echte Datei eine eigene Migrationsaufgabe.

- [2026-08-06]: Die erste Berichtskarte kam nie in Teams an. Ich hatte den Renderer-Zweig in der Logic App gebaut, das Deployment meldete `Succeeded`, der Quelldienst loggte "payload sent" — und trotzdem war der Lauf **Failed**: `The template function 'select' is not defined or not valid.` `select()` ist eine **Power-Automate**-Funktion; die Workflow Definition Language der Logic Apps kennt sie nicht, hat ueberhaupt keine map-Funktion, und **validiert Ausdruecke erst zur Laufzeit** — ein erfolgreiches `az deployment group create` beweist also gar nichts. Zweiter Fallstrick derselben Klasse: `"@{expr}"` interpoliert zu einem *String*, ein Array braucht `"@expr"` ohne Klammern; ein FactSet mit einem String haette genauso still versagt. → Bei Logic Apps ist der einzige Beleg ein **echter Lauf**: nach jedem Deploy `runs?$top=1` abfragen und den Status pruefen, nicht den Deployment-Status. Und wenn eine Zielplattform keine Transformation kann, transformiere **vor** dem Senden — der Envelope liefert die `{title, value}`-Paare jetzt fertig, was den Renderer auf eine unbedingte Referenz reduziert und ganz nebenbei das Escaping-Problem bei Anfuehrungszeichen in Dienstnamen erledigt.

- [2026-08-05]: The drift detection I had just built to catch silent providers **cleared two providers that were in fact dead**. `kaseya-itglue` (`IT Glue`) and `gravityzone-bitdefender` (`cloudgz.gravityzone.bitdefender.com`) both matched a name in `components.json`, so the check reported "filter is fine" — but those names belong to entries with `"group": true`, and a Statuspage incident **only ever references group members, never the group**. The filter could never match an incident, and the very alert meant to surface that was silenced by its own check. Verified against live data: with group resolution GravityZone goes from 0 to 21 of 33 incidents. → When validating a filter against a catalogue, validate it against **exactly the objects the filter is applied to**, not merely against the catalogue's name list — otherwise the check confirms a hierarchy level that the data never uses. And treat a self-written health check as untested until it has run against real payloads for every configured provider: I only found this because I re-measured all five filters instead of trusting the two I had already "fixed".

- [2026-08-05]: Provider logos rendered as broken images in Teams (alt text "Status"), and I first blamed the card markup. Measuring all 24 configured hosts against four favicon services showed two independent defects in one URL: (1) `https://www.google.com/s2/favicons?domain=…` answers **301** to `t{0..3}.gstatic.com/faviconV2?…` for *every* domain — the image is fetched by the Teams client, which does not follow that cross-origin hop; (2) for hosts Google has never crawled (`status.zendesk.com`, `wedos.status.online`) the chain ends in **HTTP 404** with a 726-byte placeholder body — byte-identical for both, which is what made it recognisable. Addressing the redirect *target* directly returns 200 in one hop, and with `fallback_opts=TYPE,SIZE,URL` even the two 404 hosts yield a real brand icon. → When an asset URL is resolved by a *third-party client* rather than by our own code, `curl -L` proves nothing: check the status code and hop count **without** following redirects, because that is what the client sees. And verify an image fix by *looking at the bytes* — a 200 can still be a generated placeholder rather than the brand logo.

- [2026-07-30]: Five providers (`claude`, `cloudflare`, `linkedin`, `zendesk-helpcenter`, `gravityzone-bitdefender`) plus `langdock` had silently reported **zero incidents for weeks** while every poll logged `providersSucceeded: 24` and no error. Four independent causes, all invisible in the logs: (1) YAML parses an unquoted `componentFilter: a, b, c` as **one** string, which was then substring-matched verbatim and never hit a real component name; (2) filters naming components the provider had since renamed (`1.1.1.1` → `Recursive DNS`, `Member experience` → gone, Zendesk `Help Center` → `Knowledge`); (3) the zendesk-ssp filter matched incident *titles* because the code assumed service names needed a second round-trip — they were in `included[].attributes.serviceName` all along; (4) BetterStack moved the incident id from `<link>` to the `<guid>` fragment, so `extractIncidentId` returned null for all 468 feed items. → **"Adapter succeeded" is not "adapter is working."** A count of zero after filtering deserves the same suspicion as an exception: log the pre-filter count alongside the post-filter one, and validate a fully-discarding filter against the provider's own catalogue (`/api/v2/components.json`, `/api/ssp/services.json`) instead of waiting for a human to notice the silence. When an upstream feed is the input, assert on real captured payloads — every one of these bugs reproduced instantly against live data and none was caught by fixtures written from the old format.

- [2026-07-30]: Before fixing the silent-adapter bugs above, checked what the *first poll after the fix* would emit — and found a trap: `RESOLVED_KEYWORDS` lacked `"recovered"`, which is exactly how BetterStack words its automatic recovery updates. Repairing the id extraction alone would have marked all 50 Langdock incidents `open` and posted 50 "Störung gemeldet" cards in one cycle. → When a fix makes a provider visible again, compute the notification blast radius *before* deploying: run the fixed adapters against live endpoints and count how many incidents come back `open`. `diffIncidents` only notifies on `!existing && status === "open"`, so resolved history is absorbed silently — but a status-classification bug turns that safety net into a flood.

- [2026-07-30]: The half-dead alert ("polled cleanly for 7 days but never returned an incident") fired for `wedos` and `kaseya-itglue`, both of which were perfectly healthy — WEDOS genuinely had `"incidents": []`, and Kaseya's `IT Glue` filter is valid but narrow on a 424-component page. → An absence of events is not evidence of a defect. Alert on a *verdict* ("this filter matches no component the provider publishes"), never on mere silence, or the alert trains its audience to ignore it. Also: `formatDuration` hard-coded English `"7 days"` and the string was interpolated into a German sentence ("Seit 7 days sauber gepollt") — keep machine-formatted values that cross into localised sentences language-neutral (`7d`).

- [2026-07-08]: A Dependabot dev-dependencies group bump pulled TypeScript to 7.0.2, which crashes `@typescript-eslint` 8.x at lint time (`TypeError: Cannot read properties of undefined (reading 'Cjs')`) → keep `typescript` pinned to `^6` until `typescript-eslint` officially supports TS 7; when a grouped Dependabot bump fails CI, reproduce `pnpm lint`/`build`/`test` locally on the branch and pin back the single offending package rather than closing the whole group. (Also: a Prettier version bump in the same group reformats existing files — run `pnpm format` on the branch so CI's `prettier --check` passes.)

- [2026-06-22]: Teams cards rendered as empty boxes after the redesign. I twice guessed the wrong cause from card *content* (`bleed`, then `msteams.width`) and even re-sent demo cards — the real cause was the **payload envelope**: the Teams Workflows webhook ("Post card in a chat or channel" with `string(variables('Body'))`) expects the **bare Adaptive Card** as the HTTP body, NOT the legacy connector's `{ type: "message", attachments: [{ contentType, content }] }` wrapper. The wrapper makes the flow post an empty card; flow runs still report "Succeeded". → For Teams Workflows webhooks, POST the bare card object. When a card renders blank, isolate *envelope vs content* first with a minimal "HELLO" TextBlock sent both with and without the wrapper, before suspecting any card property. Unit tests and the official `adaptivecards` object model both parse the wrapped card as "valid", so neither can catch this — only a real send (or knowing the flow's expected format) reveals it.

- [2026-05-10]: Considered an MCP server to expose configuration tools to an LLM, when the tools are nothing more than CRUD over a YAML file → If the tool layer adds no intelligence, an OpenAPI REST API is the better fit: easier to host, test, document, and connect to enterprise LLM platforms (Langdock supports MCP and OpenAPI equally well, but the latter requires less ceremony per assistant). Keep MCP for cases where stateful sessions, sampling, or streaming actually matter.

- [2026-04-23]: Built and kept an Azure Functions + Bicep + Action-Group + Alert-Rule stack for a workload that is a 5-minute cron polling ~15 HTTP endpoints → Match infrastructure weight to the actual workload. For a tiny cron-like service, a single container on existing host infrastructure (here: the Raptus Synology NAS) beats a multi-service cloud setup on cost, operational surface and reviewability. Stop accepting "it's cheap, it'll do no harm" as a reason to keep over-engineered infrastructure around.
- [2026-04-23]: After translating log/error strings to English, the test assertions still matched the old German strings and `pnpm lint` had unformatted files — baseline on main was red → When a large edit pass changes user-visible strings, run the full `pnpm build && pnpm test && pnpm lint` *before* committing, not only the narrow subset touched. Translation commits in particular need a full-suite check.
- [2026-04-15]: Documentation not updated immediately after code/config changes (provider list in `ADAPTERS.md`, adapter table in `PLAN.md`, filter task and risks in `ROADMAP.md` remained stale until the user explicitly asked) → Documentation update is part of every change. After each edit, actively check which documentation sections describe the changed area and update them in the same pass.
- [2026-04-15]: Proposed a realistic browser user-agent as a workaround for Sophos' blocked API → Browser impersonation is explicitly forbidden by `docs/CONFIGURATION.md` (section "HTTP User-Agent") because it borders on a ToS violation. When blocked, choose one of the documented alternatives (contact the provider, HTML scraping adapter, or consciously defer the provider).
- [2026-04-15]: Treated the Sophos API endpoint as "reachable" because HTTP status 200 was returned — but the body was a 404 HTML page → HTTP status code alone is not proof of a valid response. Always additionally check Content-Type and wrap JSON parsing in try/catch. Atlassian Statuspage returns an HTML error page with status 200 when the public API is disabled.
